## 1. P2 目标、范围与准入条件

### 1.1 目标

让知识内容**有负责人、有审核、有版本、有有效期、有纠错闭环**，并且治理动作本身可审计、可重放。

试点用户在 P1 闭环之上新增能完成：

```text
写 Wiki 草稿 → 关联来源文档 → 提交审核 → 他人审核通过 → 发布并进入检索
→ 页面显示负责人/有效期 → 到期前收到提醒 → 用户纠错反馈被分派 → 修订后闭环
→ 撤稿后按既定时限从检索中消失（且旧引用不可读）
```

四条必须同时成立的性质：

| 性质 | 判据（P2 硬门槛的来源） |
|---|---|
| **不泄露** | 未发布（草稿/待审/退回）与已撤稿内容，在检索与 Prompt 中 0 命中 |
| **不丢稿** | 并发编辑冲突必显式失败（409），服务端永不静默覆盖、永不自动合并 |
| **不重复索引** | 发布/撤回/重试的重复投递不产生第二份有效索引（沿用 P1 幂等账本模式） |
| **可重放** | 提醒、发布、同步失败都能重放且不重复轰炸，不靠进程内定时器 |

## 3. 核心设计决策

格式：决策 → 理由 → 代价 → 被否方案。每条都对应一个 ADR（§14）。

### D-01 Wiki 正文的权威源是 MySQL，不是 MinIO

- `wiki_page` / `wiki_revision` 存正文（`MEDIUMTEXT`，Markdown 源文本）。引擎索引是派生物，可随时从 `wiki_revision` 全量重建。
- 与 P1 的分工：上传文档的权威在 **MinIO 原件**；Wiki 的权威在 **MySQL 行**。二者恢复路径不同，必须在运维手册写清（否则运维会以为 MinIO 里有 Wiki）。
- 代价：Wiki 备份完全依赖 mysqldump；`metadata_json` 一律 `MEDIUMTEXT`，不用 JSON 列（ADR-005：MySQL 规范化会让读回字节 ≠ 写入字节，哈希链必错）。
- 被否：正文写 MinIO 对象 + DB 存指针。多一套孤儿对象对账，收益只有大正文（本期内文上限 200 KiB，不需要）。

### D-02 三轴状态模型：审核态 / 同步态 / 新鲜度正交

把"审核到哪一步"和"引擎同步成不成功"塞进一个状态字段是本项目在 P1 已经踩过的同类坑（删除 Saga 一旦与入库状态耦合，重放就产生第二份索引）。因此：

| 轴 | 载体 | 取值 | 谁写 |
|---|---|---|---|
| 审核态 | `wiki_page.status` | `DRAFT / IN_REVIEW / PUBLISHED / RETRACTING / RETRACTED / ARCHIVED` | 用户与审核人动作 |
| 修订态 | `wiki_revision.status` | `DRAFT / PENDING / APPROVED / REJECTED / SUPERSEDED` | 审核动作 |
| 同步态 | `wiki_sync_task.status` | `PENDING → CLAIMED → RUNNING → SUCCEEDED`，分支 `RETRY_SCHEDULED / FAILED / COMPENSATION_REQUIRED / DEAD_LETTERED` | worker |
| 新鲜度 | `wiki_page.freshness` | `FRESH / STALE / EXPIRED`（派生位，不是状态机节点） | 调度器 |

- 过期**不**把 `PUBLISHED` 改成 `EXPIRED`：过期但已发布的页面是"需要治理"，不是"状态迁移"。混进状态机会让 `IN_REVIEW → PUBLISHED` 的边表出现语义分叉。
- `wiki_page.published_revision_id` 是指针：检索结果回查 MySQL 时以它为准，指针不匹配的引擎命中一律丢弃并计数（同 `WeKnoraAdapter` 的 `dropped_by_unsupported_citation` 模式）。

### D-03 新版本 = 新索引，不原位覆盖

发布 `revision_no = N+1` 时创建新引擎文档（键含 `pageId + revisionNo`），确认 N+1 可见**之后**才下线 N。

- 理由：沿用 §15.7"向量维度变化通过新索引并行构建和切换，不原位覆盖"与 P1 文档版本族的同一逻辑——避免"引用还在、内容已被覆盖"。
- 代价：短暂窗口内两份索引共存 → 回查 `published_revision_id` 保证只认一份；旧版本下线失败进补偿，不影响新版本生效。

### D-04 发布与撤回分主题、分消费者组，撤回失败绝不进重试主题

| 主题 | 消费者 | 失败语义 |
|---|---|---|
| `kb.wiki.sync.v1` | `WikiSyncConsumer`（worker） | 暂时性错误进退避（`backoff_base_ms × 2^attempts`，复用 `RetryPump` 算法，`next_run_at <= now` 认领） |
| `kb.wiki.retract.v1` | `WikiRetractConsumer`（worker，独立组） | 失败置 `COMPENSATION_REQUIRED`，补偿入口是重新发起 `POST /wiki-pages/{id}/retract`；**不进**任何 retry 主题 |

- 理由：AGENTS.md §8 的既成教训——删除类操作若被入库消费者重放，会把正在下线的对象重新索引出第二份有效索引。Wiki 撤稿同理，且 `sync`/`retract` 必须分消费者组，避免一个组的积压阻塞另一个。
- 分区键：`pageId`（同页面严格有序）。header 沿用 P1 五件套，**空值不写 header**。

### D-05 治理不新增角色枚举，用指派表 + capability

- 新权限串：`wiki:read`、`wiki:read-draft`、`wiki:write`、`wiki:submit`、`wiki:review`、`wiki:publish`、`wiki:retract`、`wiki:govern`。
- `wiki:review` **不写死在角色 rank 里**，而由 `wiki_review_assignment`（空间/知识库 → 用户）计算。默认映射：`OWNER/ADMIN` 具备；`CONTRIBUTOR` 不自动具备。
- 理由：动 `WorkspaceRole` 枚举会让 P1 的授权矩阵证据（`05-verify-authz.py`）整体作废并需重跑；用指派表是加法。
- **服务端强制**：`revision.author_id != reviewer_id`，自批一律 `ACCESS_DENIED`(403)，并写审计。审核人不能是页面当前负责人时？——允许，但必须在审计里记录 `reason_code`。
- 草稿默认可见范围：作者 + 被指派审核人 + `OWNER/ADMIN`。`VIEWER` 无 `wiki:read-draft`，因此拿不到草稿——这条要有专门负向用例（G-泄露）。

### D-06 Wiki 归属已有知识库作用域，不新建 ACL 模型

- `wiki_page.kb_id` 非空，复用 `knowledge_base.acl_version` + `AclCacheService` 的版本化缓存键机制。
- 撤权即时生效直接继承 P1 语义：权威在 MySQL，Redis 只是加速件；缓存异常回源，不放宽判定（fail-close）。
- 代价：Wiki 不能跨知识库共享。本期不做，登记为待评估项（§15）。
- 被否：为 Wiki 建独立 ACL 表。等于把 P1 最难验证的部分重做一遍，且两套 ACL 语义迟早漂移。

### D-07 冲突处理：显式失败 + 服务端算差异，不做自动合并

- 写请求必须带 `If-Match: "<revision_no>"`（强 ETag）；不匹配 → `VERSION_CONFLICT`(409)，响应含当前 `revision_no` 与最新修订的 `body_digest` 前 12 位（**不返回他人正文**，避免向无 `wiki:read-draft` 的人泄露内容）。
- 差异由服务端计算：`GET /wiki-pages/{id}/revisions/{from}/diff/{to}` 返回行级增删（Java 侧 LCS，正文上限 200 KiB 下可接受）。
- 代价：用户需手工搬动改动。换来的是"永不静默覆盖"可被一条测试证明。
- 被否：三方自动合并。无法证明合并正确性，且与"每条断言可追溯"的项目纪律冲突。

### D-08 通知只做站内，不接外部邮件/IM

- 提醒落 `notification`（站内收件箱）+ 治理视图待办；无外部网络出口。
- 理由：红线——全内网离线可复现；compose 栈内无邮件服务；接外部推送等于引入外连，`10-verify-offline.py` 必失败。
- 若组织确有内网邮件网关：作为可插拔 `NotificationChannel` 的独立变更，需新 ADR + 业务签字 + 断网复跑，不在本期默认路径。

### D-09 提醒/发布/同步一律表驱动，不用进程内定时器

- `wiki_reminder`（负责人到期提醒、审核超时提醒、纠错逾期提醒）+ `wiki_sync_task`，认领条件 `next_run_at <= now`，进程重启不丢。
- 幂等：`eventId = UUID.nameUUIDFromBytes(pageId + ":" + rule + ":" + dateBucket)`，重复扫描被 `event_consumption` 账本吸收（照 `RetryPump` 的确定性 ID 写法）。
- `dateBucket` 取 UTC 日期截断（如 `20261120`），保证"同一天最多提醒一次"跨重启成立。
- 这条直接对应退出条件"提醒失败可重放"。

### D-10 来源引用：保存时校验 + 读取时回查

- `wiki_source`：`revision_id, source_type(DOCUMENT|WIKI_PAGE), document_id, document_version, chunk_index, locator, content_digest, acl_version`。
- 保存/提交时：校验 actor 对每条来源可见（不可见 → `ACCESS_DENIED`，跨租户 → 404）。
- 发布与每次读取时：回查来源文档仍 `READY` 且版本存在；已失效 → `freshness = STALE` + 写 `wiki_source_broken` 计数，**不阻断发布**（否则一处失效锁死全站治理），也不把断链来源当作可信依据展示。
- 循环引用（Wiki 引用 Wiki）：允许，但撤稿时反查依赖并给负责人站内提醒，不级联下线。

### D-11 纠错闭环：关闭必须关联修订或显式 WONTFIX

- `correction_case`（来源 `chat_feedback`）状态 `NEW → TRIAGED → ASSIGNED → RESOLVED | REJECTED | WONTFIX`。
- `RESOLVED` 必须填 `resolution_revision_id`（或 `resolution_document_id`）；否则 `VALIDATION_FAILED`。
- 理由：没有这条约束，"闭环"会退化成"标记已读"，运营指标不可信。
- 隐私：`chat_feedback.comment`（≤1000 字，可能含答案/原文片段）**绝不进报告、日志、治理视图摘要**；查询 API 仅返回给被指派人与 `wiki:govern` 持有者（红线 1）。

### D-12 发布同步与问答共用模型额度但独立并发闸

- 新配置 `kb.wiki.sync-max-concurrent`（默认 2），与 `kb.model.max-concurrent`（默认 5）分账；发布不抢占在线问答信号量。
- 批量发布（一次审核通过多页）走队列削峰，单页正文上限 200 KiB、分片沿用 P1 `Chunker`。
- 理由：P1 风险表"模型/GPU 容量不足"是真实约束；治理动作（尤其全量重建）不可挤掉在线问答。

## 5. 状态机（新增冻结件 `p1/contracts/state-machine-wiki.md`）

### 5.1 审核态迁移表

| 迁移 | 触发 | 前置校验 | 失败分类 |
|---|---|---|---|
| `DRAFT → IN_REVIEW` | `POST /wiki-pages/{id}/submit` | `current_revision_no` 与提交携带的 `If-Match` 一致；actor 有 `wiki:submit`；至少 1 条 `wiki_source`；`valid_until` 非过去 | 版本不符 → `VERSION_CONFLICT`(409)；来源不可见 → `ACCESS_DENIED`(403) |
| `IN_REVIEW → PUBLISHED` | `POST /wiki-revisions/{revId}/approve` | actor 有 `wiki:review`；`revision.author_id != actor`；页面当前 `IN_REVIEW` | 自批 → `ACCESS_DENIED`；状态不符 → `INVALID_STATE_TRANSITION`(409) |
| `IN_REVIEW → DRAFT`（退回） | `POST /wiki-revisions/{revId}/reject` | 同上角色约束；必填 `decision_note` | `VALIDATION_FAILED`(400) |
| `PUBLISHED → PUBLISHED`（新版本） | 审核通过 `revision_no = N+1` | 旧 N 仍在索引；写 `published_revision_id` 指针 | 同 approve |
| `PUBLISHED → RETRACTING` | `POST /wiki-pages/{id}/retract` | actor 有 `wiki:retract`；写 `wiki_sync_task(operation=RETRACT)` | 状态不符 → `INVALID_STATE_TRANSITION` |
| `RETRACTING → RETRACTED` | 引擎确认索引消失（回查可见性） | 同步任务 `SUCCEEDED` | 任一步失败 → 任务 `COMPENSATION_REQUIRED`，页面**停在 `RETRACTING`，绝不回 `PUBLISHED`** |
| `任意非 IN_REVIEW → ARCHIVED` | `POST /wiki-pages/{id}/archive` | 有 `wiki:retract`；`IN_REVIEW` 中的页面须先退回 | `INVALID_STATE_TRANSITION` |

规则（与 P1 一致，逐条落到代码与用例）：

1. 每次迁移 `UPDATE ... WHERE status = 前置态`，`affected = 0` 即重新读状态再判定，非法迁移返回 `INVALID_STATE_TRANSITION`(409) **并写审计**。
2. `RETRACTING` 状态下检索与引用预览一律拒绝（不依赖引擎是否已删干净）——与 P1 `DELETING/COMPENSATION_REQUIRED` 挡住检索的做法同构。
3. 永久性错误（`VALIDATION_FAILED`/`ACCESS_DENIED`/`CROSS_TENANT_ACCESS`/`WIKI_SOURCE_UNAVAILABLE`）不进 retry；只有暂时性错误（`ENGINE_*`/`STORAGE_UNAVAILABLE`/`MODEL_UNAVAILABLE`/`CONCURRENCY_LIMITED`）按 `backoff_base_ms × 2^attempts` 退避。
4. 超过 `max_attempts` → `DEAD_LETTERED` + `kb.wiki.dlq.v1` 信封；页面停在原状态，治理视图可见并可受控重放。

### 5.2 必须补的负向用例（AGENTS.md §5：新状态必须补迁移表**与**负向用例）

| 用例 | 期望 |
|---|---|
| 对 `DRAFT` 页面执行 approve | 409 `INVALID_STATE_TRANSITION`，审计有 `DENY` 记录 |
| 作者自批 | 403 `ACCESS_DENIED`，无审计外的副作用 |
| `If-Match` 指向旧 `revision_no` 保存 | 409 `VERSION_CONFLICT`，页面内容不变 |
| 两个并发 `submit` 同一页 | 恰一个成功，另一个 409，无第三个修订行 |
| approve 与 retract 并发 | 终态唯一，索引不出现"既发布又撤稿"的两份有效可见性 |
| 重复 approve 同一 revision | 幂等：不产生新修订、不重复发同步任务 |
| 撤稿后检索同一 `pageId` | 0 命中（时限内），`citation` 预览返回 409/404 |
| 草稿正文关键词跑全库检索 | 0 命中；引擎请求发出前草稿不可达（空 scope 不发请求） |
| 跨租户命中 `pageId` / `revisionId` / `caseId` | 404，`CROSS_TENANT_ACCESS` 只写审计不作响应 |
| 撤稿期间引擎不可用 | 停 `RETRACTING` + 任务 `COMPENSATION_REQUIRED`，**不回 `PUBLISHED`、不进 retry 主题** |
| worker 在 sync `RUNNING` 时被 kill | 租约到期后重新认领，`attempts+1`，无第二份索引 |
| 提醒规则同一天扫描两次 | 站内通知仍恰一条（`date_bucket` 唯一键 + `event_consumption`） |

## 8. 检索侧集成（治理与问答的接缝）

1. **入库**：`WikiSyncConsumer` 把 `PUBLISHED` 修订按 P1 `Chunker` 分片，附元数据 `tenant_id / workspace_id / kb_id / page_id / revision_no / source_type=WIKI_PAGE / visibility`。缺任一必需元数据 → 拒绝索引并计数，不发引擎请求。
2. **召回**：引擎候选在进入 Prompt 前逐条回查 MySQL——页面 `status = PUBLISHED`、`published_revision_id == 候选 revision_id`、ACL 通过。任一不满足 → 丢弃 + `dropped_by_stale_wiki` 计数。**引擎过滤只是缩小候选，不是授权判定**（ADR-002）。
3. **引用**：Wiki 引用落 `citation(source_type=WIKI_PAGE, page_id, page_revision_no)`；预览走 Java 授权代理，前端不直连引擎。
4. **问答可见性**：`RETRACTING/RETRACTED/ARCHIVED` 的页面在检索层被挡（同 P1 对 `DELETING` 的处理），旧会话里已有的 Wiki 引用在预览时按 `acl_version`/状态二次判定，拒绝即 404/409，不返回缓存正文。
5. **基线可比**：G-4 冻结的"无 Wiki 语料基线"与"含 Wiki 语料基线"分两轮跑、分开报告，否则 Recall@5 变化无法归因（红线 4：引用指标必须注明口径）。

| Wiki 列表/详情 | loading / empty / 403 / stale | 动作按钮由服务端 capability 决定，前端不做权限判断 |
| 草稿编辑 | dirty / saving / 409 冲突 | 409 时保留本地稿并提供"比较/刷新"，**禁止静默覆盖** |
| 审核队列与差异视图 | 待审/已审 | 差异由服务端 `/diff/` 提供，前端不自行 diff 出"真相" |
| 修订历史 | 分页 | 展示 `revision_no` + 作者 + `body_digest` 短前缀 |
| 治理面板 | 负责人/有效期/新鲜度/待办 | 只读汇总 + 显式 PATCH |
| 纠错工单 | 分派/关闭必填关联修订 | 关闭无 `resolution_revision_id` 时表单不允许提交（后端仍独立校验） |
| 通知中心 | 未读 | 不展示正文摘要之外的来源内容 |

DoD（沿用前端方案 §12.1）：OpenAPI 生成类型无偏差；每页有 loading/empty/error/403/stale/success；Markdown 渲染净化（禁 raw HTML、禁外链脚本）；无秘密/正文写入 URL、localStorage 或第三方日志；键盘可完成"读页面→提交审核"主流程。
