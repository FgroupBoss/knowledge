# ADR-005 数据模型：无外键、UUID 字符串主键、Flyway 单向迁移，引擎镜像与业务表分家

- 状态：已采纳（2026-10-31）
- 背景：P0 的表要在 10 天里反复重建、灌评测语料、做恢复演练；同时引擎（ADR-003）随时可能换实现，
  不能把召回侧的数据结构焊死在业务模型上。
- 决定：
  1. 主键一律 `CHAR(36)` 存 UUID 规范字符串（不用自增，避免跨库恢复/分库时撞号，也不暴露规模）；
     业务唯一性用带前缀的唯一键表达（`uk_doc_acl`、`uk_outbox_event_id`、`uk_idem` 等）。
  2. 身份主体用 `(issuer, subject)` 复合唯一键而不是裸用户名，为后面接企业 IdP 留出边界；
     `user_code` 目前是**全局唯一**（不是租户内唯一），这是已知约束，见 P1 backlog。
  3. 时间列一律 `DATETIME(3)`、一律 UTC、由应用写入（不用数据库时区默认值），
     跨机恢复后不出现"时间跳 8 小时"。
  4. **不建 FOREIGN KEY**：一致性由业务事务 + 对账保证（孤儿对象、幽灵索引都是显式计数项），
     避免恢复演练和批量导入时被约束顺序卡住。
  5. 迁移文件只在 `portal-poc/src/main/resources/db/migration/` 生效，
     `p0/db/migration/` 是交付副本，由 `scripts/11-sync-migrations.sh` 单向镜像并用 SHA-256 强校验一致，
     交付包里出现"两份 V3 长得不一样"这种事故直接被脚本挡掉。
  6. 引擎侧召回数据（`engine_kb / engine_document / engine_chunk`）与业务表分家存放，
     只作召回与取证，任何权限判定都必须回 MySQL 复核（ADR-002）。
- 后果：
  - 正面：删库重建、旁路恢复、批量灌语料都很顺；换引擎时业务表不动。
  - 负面：没有外键就没有数据库级完整性，脏行只能靠对账发现——所以"幽灵索引 0、重复索引 0"
    这类计数是必须长期跑的检查，而不是上线前一次性检查；P0 期间 DDL 与 DML 共用一个账号，
    生产必须拆分（已列 P1）。
- 证据：`db/README.md`、`p0/db/migration/` 与 `portal-poc/src/main/resources/db/migration/` 的摘要一致、
  `evaluation/reports/ingest-run.md` IX/TX 家族、`evaluation/reports/fault-drill.md` FD-13~FD-15。
- 责任人 / 复测：Java + 平台运维；P1 建库建账号时验证 DDL/DML 分离，2026-11-13 前。
