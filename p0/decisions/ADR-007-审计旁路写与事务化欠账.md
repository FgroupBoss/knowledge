# ADR-007 审计事件当前是同步旁路写，允许"业务成功、审计失败"，必须在 P1 事务化

- 状态：已采纳，**含已知缺陷**（2026-10-31）
- 背景：`audit_event` 记录每次越权尝试（`DENY`）、上传、问答、夹具投毒等动作，
  是"越权 0 例"这条硬门槛的取证来源。P0 的实现是在业务路径里同步写一条审计记录，
  写失败只打 ERROR 日志，不回滚业务、也不改变判定。
- 决定：
  1. P0 保留这个行为，但把它写成显式缺陷而不是"够用"：审计的价值在于**负向事件必须留痕**，
     而现在如果 MySQL 抖动，一条 `DENY` 可能消失，取证就会低估风险。
  2. 判定顺序不变：先授权、后审计，绝不因为审计写失败而放行请求（fail-close 在授权侧）。
  3. P1 改成与业务同一事务写 outbox、再异步投递到 `kb.audit.v1`（或至少与 ADR-004 的
     outbox 复用同一张表），保证"发生了就一定留痕"；同时补审计的保留期与不可篡改要求。
  4. 审计内容红线：只记 `(actor, action, resource, result, errorCode, traceId, 计数型详情)`，
     绝不写 Prompt 正文、文档正文、对象键、凭据；`DENY` 里连被拒绝的文档标题都不记，
     避免通过审计反查他人文档是否存在（跨租户一律 404 而不是 403，同理）。
- 后果：
  - 正面：P0 的取证是自洽的——本轮演练里 `chat%` 的 `DENY` 计数为 0 与跨租户引用 0 例可以互相印证；
    一旦审计缺失，别的用例不会假装通过（多条用例直接依赖审计计数）。
  - 负面：**目前不能承诺审计完备性**。生产接入前必须完成事务化改造，并把"审计写入失败"变成
    可告警事件；这一条已进 P1 backlog 的阻断项列表。
- 证据：`audit/AuditService.java` 类注释、`evaluation/reports/authz-matrix.md`（DENY 计数与 26/26）、
  `evaluation/reports/quality-baseline.md` EV-12（问答期 DENY=0、跨租户引用=0、跨租户 Chat=0）。
- 责任人 / 复测：Java + 安全；P1 第一个迭代完成事务化并用故障注入验证"业务成功但审计必须存在"（2026-11-20 前）。
