# ADR-009 离线验证的口径：业务网真的没有出口，但"宿主机门户"决定了这一步能证到什么程度

- 状态：已采纳（2026-10-31）
- 背景：方案要求"切断公网 DNS/出口后从冷启动开始完成上传、索引、提问和引用，并抓取外连日志证明
  没有静默云回退"。P0 环境里门户 JVM 与 Ollama 都跑在宿主机，MySQL/Redis/Kafka/MinIO 跑在 Compose。
- 实测到的形态约束（这是本 ADR 的起因）：
  把 `p0-ingress` 也改成 `internal: true` 之后，Docker Desktop **不再为该网络上的服务生效端口发布**
  （`docker port` 空、宿主 `127.0.0.1:13306` 连不上）。也就是说"依赖全切 internal + 门户仍在宿主机"
  这个组合根本跑不起来，只能得到一次失败的环境切换，而不是断网证据。
  已用一次性探针容器把这条约束固化成可复现用例（OF-02），不靠口头描述。
- 决定：P0 的"断网"按三条独立证据取证，缺一即不算通过：
  1. **网络面**：业务网 `kb-p0_p0-backend` 本身是 internal——在上面起一次性容器实测
     外部域名解析失败、外部 TCP `Network is unreachable`（OF-01）。生产部署里门户与依赖都在这张网上。
  2. **进程面**：完整冷启动（建空间→建库→上传→索引 READY→问答→引用预览）期间持续采样
     门户 JVM 与 Ollama 两个 PID 的全部 TCP 连接，观测到的远端只有回环，公网远端 0 条（OF-03~OF-08），
     并且窗口内主动跑了十几轮问答，避免"没流量所以没外连"的假证据。
  3. **配置面**：`P0_OFFLINE_ENFORCED=true` 时把推理端点写成公网 IP 必须**启动失败**
     （`EngineConfig.assertNoCloudModel` → `IllegalStateException`），杜绝"配错就静默上云"（OF-09）。
- 后果：
  - 正面：三条证据互相独立，任何一条被推翻都不影响其它两条的可信度；
    结论"没有静默公网回退"在 P0 形态下是可辩护的。
  - 负面（必须如实写进验收包）：这套口径**没有**证明"门户与依赖在同一张不可出网的网上仍能跑通"，
    因为宿主机门户形态下这个组合不存在。真正的容器化全内网冷启动是 P1 前置项：
    把门户打进镜像、进 `p0-backend`，再用 `docker-compose.offline.yml` 跑同一条链路。
    在完成之前，Go/No-Go 里"断网可用"按本 ADR 的三条证据判定，并在决议文档里标注口径。
- 证据：`evaluation/reports/offline-drill.md`（OF-01~OF-10 全通过）、
  `compose/docker-compose.offline.yml` 与其在宿主机形态下的失败记录。
- 责任人 / 复测：平台运维（门户镜像与全内网 Compose）；P1 第一周内完成并复跑同一组用例（2026-11-06 前）。
