# ADR-011 页面态 / 修订态 / 同步态三轴正交，W1 只把前两轴接进代码

- 状态：已采纳（PAGE/REVISION 轴已接；SYNC 轴只有边表）（2026-11-01）
- 背景：把"能不能看"和"索引好了没"和"是不是过期"压进一个 `status` 列是这类系统最常见的返工点
  （P1 的 `document.status` 已经为此加过 `COMPENSATION_REQUIRED`）。D-02 的取舍是：
  拆三轴会让状态机变大（21 条边）、需要更多负向用例；换来的是撤稿失败不会把内容"退回已发布"。
- 决定：
  1. PAGE 6 态、REVISION 5 态、SYNC 8 态各自独立迁移，彼此只通过事务内的事件相连；
     `freshness` 是**派生位**，没有自己的出边，只有 W3 的扫描器写它。
  2. 状态迁移一律 `UPDATE ... WHERE status = 前置态`，0 行即 `INVALID_STATE_TRANSITION`(409) 并写审计；
     `WikiStateMachine.EDGES` 与 `p1/contracts/state-machine-wiki.md` 的表格由
     `p1/scripts/24-check-contracts-p1.py` 逐条比对，缺边即 ERROR（扩展门禁，不放宽）。
  3. **`submit` 不总伴随页面态迁移**：已发布页面提新修订只走 R1，页面留在 `PUBLISHED`，
     审核通过才由 E4/R4 一次性换指针。所以实现里不能要求"submit 必须有 PAGE 出边"，
     否则 E4/R4 永远不可能产生——这是本轮踩过并写进契约的一条。
  4. W1 只接前两轴。SYNC 轴的 8 态与三个主题先落契约、表与边表，**不写消费者**：
     `wiki_sync_task` 停在 `PENDING`，`outbox_event` 里不得出现 `kb.wiki%` 主题行。
- 后果：
  - 正面：撤稿半途失败可以停在自己的补偿态而不污染可见性；状态机可被脚本核对，不靠文档自觉。
  - 负面：三轴组合的读侧视图要靠 capability 与派生位拼，前端不能自己算"真相"；
    SYNC 轴的退避/租约/幂等**在真引擎上未验证**（§13.1 硬门槛，阻断于 backlog #1）。
  - 已知偏差：W1 没有 `RETRACTING → RETRACTING` 自环，重复撤稿现在吃 409，补偿入口留给 W2（backlog #28）。
- 证据：`p1/evaluation/reports/p2-wiki-contracts-and-w1.md` PW-04（21 条边逐条比对 + 派生位无出边）、
  PW-05/06/07/08/09（§5 负向用例）、PW-16（任务停 `PENDING` 且零 `kb.wiki%` 事件）；
  复跑 `python p1/scripts/24-check-contracts-p1.py` 与 `mvn -o clean test`。

  `p1/evaluation/reports/`（依赖 F-1，2026-11-13 后）。
