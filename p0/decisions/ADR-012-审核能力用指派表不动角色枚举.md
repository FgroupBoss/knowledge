# ADR-012 治理与审核能力用指派表 + capability，不新增角色枚举

- 状态：已采纳（W1）（2026-11-01）
- 背景：D-05。审核 Wiki 需要"能审别人的改动"这种能力，最省事的做法是加一个 `REVIEWER` 角色，
  但 `WorkspaceRole` 是冻结的枚举，且角色一旦承担治理语义就会连带放大权限（角色是全库的，
  审核能力是按库/按人给的）。P1 的教训是权限判定必须能落到**行**上，才能审计与回收。
- 决定：
  1. 审核能力只来自 `wiki_review_assignment`（`scope_type=KB|WORKSPACE` + `user_id`），
     `WikiCapabilities.compute` 里 `review = (kb.role ∈ {OWNER, ADMIN}) || assigned`；
     **不因 `CONTRIBUTOR` 角色放宽**，也不因"是作者"放宽。
  2. capability 与内容可见性分开：`readDraft = author || review || owner`，**故意不含 `write`**，
     因为"能写别的页面"不等于"能看这篇草稿"。
  3. 响应只回 capability 名单（前端据此置灰），服务端仍然每个动作重算——置灰不是授权。
  4. `retract` 与 `govern` 各自单独判定；自批由 `WIKI_REVIEW_SELF_APPROVAL` 单独拦，
     不靠"权限不足"这种含糊码，便于审计区分"没资格"和"自己批自己"。
- 后果：
  - 正面：回收审核权是删一行，不改角色、不动缓存版本以外的东西；跨租户命中一律降级 404 的语义不受影响。
  - 负面：W1 **没有指派端点**，引导靠 SQL（测试夹具直插一行），运维手册里还没有这一节（backlog #27）；
    指派表本身没有过期时间与审计回溯，批量改派要到 W3。
- 证据：`p1/evaluation/reports/p2-wiki-contracts-and-w1.md` PW-11（capability 来自指派行）、
  PW-05（自批被拒且无副作用）、PW-10（跨租户 404）；对应代码 `wiki/WikiCapabilities.java`、
  `it/WikiGovernanceIntegrationTest.java`；复跑 `mvn -o clean test`。
- 责任人 / 复测：Java＋平台运维；W3 出指派端点时补"回收后旧缓存键不得命中"的用例（2026-11-20 前）。
