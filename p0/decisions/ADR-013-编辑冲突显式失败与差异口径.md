# ADR-013 编辑冲突显式失败、差异由服务端算，拒绝自动合并

- 状态：已采纳（W1）（2026-11-01）
- 背景：D-07。两个人同时编辑同一页面时，"最后写入者赢"会静默丢稿，这正是 §13.1
  "并发编辑 0 丢稿"这条硬门槛要防的。另一个诱惑是前端自己算差异——那会把"真相"复制到每个客户端。
- 决定：
  1. 保存草稿走乐观锁：`UPDATE ... WHERE current_revision_no = :ifMatch`，
     不符即 409 `WIKI_REVISION_LOST`，**绝不静默覆盖**。当前修订是 `DRAFT` 则原地更新，
     是 `APPROVED/SUPERSEDED/REJECTED` 则新建 `revision_no+1` 的草稿。
  2. 冲突响应只给 `currentRevisionNo`、`latestRevisionNo`、`latestBodyDigest12`
     三个计数型字段，**不回传他人正文**（红线 1 与跨用户存在性泄露都在这条上）。
  3. 差异由服务端算（LCS）：返回 `addedLines/removedLines/truncated/lines[]`，
     `lines[].op ∈ {context, added, removed}`；超预算（1.5M 格或 400 行）退化成"只给计数不给行"，
     宁可少给信息也不让一次预览请求打满堆。
  4. 不做自动合并：两边草稿冲突时只给差异与摘要，合并动作交给人（审核环节的 diff 也是它）。
- 后果：
  - 正面：丢稿在数据库层就不可能出现（条件更新 0 行），审计与响应都不携带正文。
  - 负面：客户端必须处理 409 并保留本地稿，交互成本比"覆盖"高；
    差异计算对超大正文只给计数，前端需要提示"请缩小比较范围"。
  - 本轮实测到的代价：契约里"最新修订"这一条把实现打回过一次——
    4 处 `revisionLost(...)` 原本把 `If-Match` 那一行当最新修订报出去，
    客户端按错的号重试仍会失败；修复方式是新增 `findLatestRevision`（且刻意 `NULL AS body`）。
- 证据：`p1/evaluation/reports/p2-wiki-contracts-and-w1.md` PW-06（用例 3 的三字段与"无正文"断言）、
  PW-07（并发 `submit` 恰一成功、无第三修订）、PW-13（预算降级）、
  本轮缺陷段落第 2 行；复跑 `mvn -o clean test`（`WikiDiffTest` 8 例 + `WikiConcurrencyIntegrationTest` 9 例）。
- 责任人 / 复测：Java；W3-06 前端冲突面板落地后补一次窄屏人工验收（依赖 Q-2 拍板）。
